# 架构与后续方向

Douban Import 采用自己的应用结构来继续维护现有能力。此次重构将原来集中在入口中的应用职责与豆瓣业务实现分开，同时保留已使用的数据字段和工作流。

## 当前职责划分

| 目录 | 职责 |
| --- | --- |
| `src/main.ts` | Obsidian 插件入口 |
| `src/app/` | 生命周期、命令注册、设置迁移与应用服务协调 |
| `src/sources/douban/` | 豆瓣搜索、页面解析、认证、来源模型与来源请求 |
| `src/sync/` | 个人收藏的范围选择、预览、执行、状态及结果报告 |
| `src/settings/` | 配置模型、设置界面和配置导入导出 |
| `src/templates/` | 默认模板、预设、变量与预览 |
| `src/notes/` | 本地笔记的创建、继续及关联 |
| `src/userdata/` | 用户属性和正文的提取、差异、合并及保护 |
| `src/platform/` | Vault 文件操作，以及桌面/移动端网络实现 |
| `src/shared/` | 公共工具及仍由既有流程共享的类型 |
| `src/ui/`、`src/i18n/` | 交互界面与语言文案 |

应用层当前包含 `commands.ts`、`SettingsStore`、`SearchService`、`SyncService`、`ImportService` 和 `StatusBarController`。命令注册、配置持久化、搜索、同步入口、写入与替换、状态栏显示因此有了各自的修改位置。其中 `ImportService` 集中处理路径冲突、替换准备、数据保护和写入恢复，来源解析器继续负责提取豆瓣资料。

应用层负责组装和协调能力；豆瓣页面变化主要落在来源模块；备份、合并和写入仍按现有数据规则执行。源码中仍保留部分 Douban 类名和旧模块之间的依赖，这次目录及职责拆分不等于所有旧代码已经彻底解耦。

新的结构为后续改动提供明确位置，当前优先级仍是完整保留已有功能。没有为尚未出现的需求预先引入通用插件框架或新的持久化格式。

## 兼容性边界

`doubanId`、模板变量、配置键和用户数据 JSON 属于已有使用约定。重组源码和更换插件 ID 不应顺便改变这些约定。插件 ID 改变后的配置和快捷键迁移见[迁移说明](./migration.md)。

当前 `sources/douban/models` 表示来源数据，不能把它直接视为未来本地 Work 模型。当前“豆瓣日记”类型也不同于个人 Note 页面。

示例模板位于 `examples/templates/`，与插件源码和用户 Vault 内容分开。源码来源及许可证记录在仓库根目录的 `PROVENANCE.md`。

## 后续方向

以下为设计方向，**尚未在 0.1.0 实现**，也没有冻结最终 schema。

### 本地身份与来源

本地 Work 拥有独立身份，不能用豆瓣或 Bangumi ID 代替本地身份。平台条目提供资料及初步个人记录，通过来源映射关联本地作品。来源更新与用户维护的数据需要有清晰边界。

### 页面与系列

第一阶段围绕 **Series、Work、Note、View** 组织文娱库。Series 组织作品和子系列，Work 表示用户实际收录的作品，Note 保存个人记录，View 提供浏览和汇总。

已明确系列归属的收录作品，可以复用已有 Series；没有对应 Series 时，可创建最小系列页面和所需目录。这个过程以实际收录的 Work 为起点，不因来源网站列出整个系列就自动建立所有未收录作品或空目录。系列归属不明确时，不从标题猜测成确定关系。

### 随记与展示

每个 Work 的持续随记和快捷入口是后续使用重点。Note 在导入作品时创建，还是在首次记录时创建，**仍待确定**。

基础内容应保存在普通 Markdown/YAML 中，展示增强不应成为数据唯一载体。具体属性、目录规则、迁移步骤和自动化时机在实际实现前单独确定。

## 实施原则

先确保旧功能在新结构下可用，再以少量真实条目确定新约定。按需求逐步调整身份、来源关系、系列组织和笔记流程；保留旧内容，不把一次源码重构变成未经说明的 Vault 数据迁移。
